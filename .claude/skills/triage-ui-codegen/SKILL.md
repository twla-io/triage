# triage-ui-codegen

Derive `frontend/src` from three sources:
- **`Domain.hs`** gives meaning: which cases a sum type has and what each carries, the lifecycle (which transitions leave each case), sealed types' rules, enumerations, and rankings (`Ord` instances).
- **The API contract** gives the wire: `src/api/types.ts` (generated by `npm run generate-types` from the running backend; never hand-edited) for record shapes, and the route list in `/swagger.json` for paths, query parameters, request bodies and outcome tags. Wire names follow `triage-api-codegen`'s `names-come-from-domain` (a case's tag is its constructor in lowerCamelCase), so they can be computed from `Domain.hs`.
- **`docs/decisions.md`**, narrowly: UI behaviour that a current decision explicitly states for a form or screen. Apply it; invent none.

This skill says only how those become screens. It names no Domain type, route or tag; `e.g.` marks an illustration, never a requirement.

- Read the sources fresh every time. Existing frontend code is output to check against these rules, never an example to copy.
- Never read `Api.hs`, `Transport.hs`, `Service.hs` or `Persistence.hs`: the UI derives from the spec and the published contract, not from another layer's code.
- If the sources leave something a rule needs undetermined, stop and ask. The fix belongs in `Domain.hs`, the API, or a decision.
- Rules apply to existing code. After a rule or a source changes, check every screen against every rule.

## Wire types (`src/api/wire.ts`)

### `sums-come-from-domain`
Swagger 2.0 can't express a sum type: the generated type of a sum is one object with a `type` enum and every case's keys optional, and an envelope's `detail` is untyped. So `src/api/wire.ts` declares, from `Domain.hs`:
- **each sum type crossing the wire** as an exact discriminated union, one member per constructor, with exactly that case's keys (embedded stages flattened, as the API does);
- **each use case's answer** as a union over its outcome tags, each with its exact `detail` type;
- **one narrowing function per sum type** from the generated type to the exact union, checking the tag.

Records come from `types.ts` unchanged. Only `wire.ts` imports from `types.ts`; pages and query hooks import from `wire.ts`. No `as unknown as`, and no cast anywhere else.

## Coverage and screens

### `every-use-case-has-a-place`
- **Every mutation** route is an action on the entity it acts on, offered only in the cases where `Domain.hs` defines its transition (`actions-follow-the-lifecycle`). A mutation that starts from an element of a collection (e.g. one taking a slot id) is an action on that element where the collection is shown.
- **Every collection read** is a list. A read taking a time range gets a range picker (`one-range-rule`).
- **Reads by id** are not screens: they stay API-only.

### `one-page-per-entity`
- One page per entity that has a collection read (navigation order: see Display). An entity whose elements are shown only through a collection type's read (e.g. inside a sealed collection) appears on that collection's page, with its create action there.
- A page for a sum-typed entity has one section per case, in constructor order (which is lifecycle order), each fed by that case's read.
- No other grouping: a page or section exists only because an entity, case or read does.

## Actions and forms

### `actions-follow-the-lifecycle`
A record's actions come from one exhaustive `switch` over its `type`, returning exactly the transitions `Domain.hs` defines out of that case. One such mapping per entity, shared by every screen that shows the entity. A case with no outgoing transition is read-only. Adding a constructor must fail to type-check until it is mapped.

### `client-state-mirrors-sum-types`
Client state for a value of a sum type is that type's union from `wire.ts`, never independent booleans or optional fields that could disagree.

### `forms-follow-request-types`
A form's controls are its request type's fields, labelled by their names humanized (`mustBeSeenBy` → "Must be seen by"):
- `Text` → text input; `Maybe` → the same control, optional.
- `UTCTime` → date-time picker.
- an ID → a select over that entity's collection read, labelled by name.
- an enumeration (derives `Enum, Bounded`) → a select over all its constructors.
- a sum type → a select of its constructors that reveals exactly the chosen case's controls; never independent optional fields whose combination encodes the case.
- a time the server records is not a field (the API leaves it out).

A sealed type's rule (its smart constructor's condition) is never re-implemented in the UI: Domain logic has one implementation. The server refuses an invalid value with `400`, and its message, which names the rule, is shown (`show-every-outcome`).

## Answers

### `show-every-outcome`
Every mutation and read answers `200` with `{"outcome", "detail"}`. The success tag (`ok`, or the use case's success tag) closes the form; every other tag is shown inline, as one sentence per kind, filled from the tag and its `detail`:

| Tag shape | Text |
|---|---|
| `<entity>NotFound` | "That ‹entity› no longer exists." |
| `<entity>InWrongState` | "This action doesn't apply to a ‹entity› that is ‹detail.type›." |
| `movedOn`, `<entity>MovedOn` | "Someone else already acted on this ‹entity›; it is now ‹detail.type›." |
| `<entity>Consumed` | "That ‹entity› was just taken by someone else." |
| any other | the tag humanized (e.g. `fooBarBaz` → "Foo bar baz") |

‹entity› and ‹detail.type› are humanized too.

After any answer, invalidate every query, so every list shows the current state; narrowing this would be a performance change, not a design one. A non-`200` status is an error banner with its status and body.

## Display

### `values-render-by-name`
A value shows its fields with humanized labels; an ID of another entity shows that entity's name (from its collection read); a time shows date and time; a case shows its constructor humanized. Every label is a humanized `Domain.hs` name. None is overridden or written by hand: a label that reads badly is raised as a naming question about `Domain.hs`.

### Navigation
Pages appear in the order `Domain.hs` declares their entities; the app opens on the first.

### `rank-is-the-only-color`
A sum type with an `Ord` instance that a `Domain.hs` function uses is ranked: its constructors get a graded color scale by rank, the first-ranked the strongest (red) and the last the calmest (green), any middle ones in between. Every other sum type renders as a neutral badge. Within a rank, order is shown by position, not color.

### `lists-keep-server-order`
A list renders in the order its read returns. The UI never sorts.

### `one-range-rule`
Every range picker opens on the current week, Monday to Sunday, with previous and next arrows moving by a week. No other default window.

## Implementation

- **Stack:** React 18 + TypeScript + Vite, Mantine, TanStack Query, react-router (`frontend/package.json`). No other framework.
- **Files:** `src/api/client.ts` (the one fetch wrapper: base URL from `VITE_API_BASE_URL`, JSON headers, non-`2xx` → `ApiError`); `src/api/wire.ts`; `src/api/queries/<entity>.ts` (one hook per route); `src/pages/<Entity>Page.tsx`; shared components in `src/components/`.
- **Not output:** `src/api/types.ts` (generated), `src/main.tsx`, `src/theme.ts`, `src/theme.css`, `src/components/ErrorBoundary.tsx`. Keep them as they are.
- **Check:** `npm run build` passes, and `grep -rn "as unknown" src` finds nothing.

## When unsure

Prefer a design where the UI can't reach an invalid state (the way `Domain.hs` can't construct one) over validating after the fact. If a screen seems to need something no source states, stop and ask rather than invent it.
